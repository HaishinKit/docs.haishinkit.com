rtmp

RTMP and RTMPS publishing and playback for HaishinKit.

Use RtmpConnection and RtmpStream for direct connection and stream control. For a single-stream session, register RtmpStreamSessionFactory with StreamSession.Builder.

Enhanced RTMP support

An extended RTMP standard called Enhanced RTMP is being developed by the Veovera Software Organization. Please check this repository for the specifications.

  • Enhanced RTMP also requires support on the server side. Please check the support status of the server you are using.

AV1 playback

AV1 playback uses Enhanced RTMP (av01) and the device's built-in Android decoder. It requires Android 10 or later, an available AV1 decoder, and an Enhanced RTMP server such as MediaMTX. No additional software codec is bundled. Use the normal RtmpStream.play API; codec selection follows the received stream. AV1 publishing is not implemented by this change.

AV1 playback waits up to five seconds for the renderer's initial output surface. Changing to or from AV1, or changing its decoder configuration during playback, is rejected and logged. Close the stream and create a new playback stream for such changes. Repeated identical AV1 configuration records are accepted.

VP8 / VP9 publishing and playback

Enhanced RTMP uses vp08 for VP8 (v2) and vp09 for VP9. Both directions use only Android's installed MediaCodec encoders/decoders. No additional codec is bundled. The server and the peer must support the same Enhanced RTMP codec; VP8 in particular requires a v2-capable implementation. Support for AV1 or HEVC alone does not imply VP8 support.

Select a profile before starting publication, for example:

stream.videoSetting.profileLevel = VideoCodecProfileLevel.VP8_MAIN
// Or, on Android 7.0+:
stream.videoSetting.profileLevel = VideoCodecProfileLevel.VP9_PROFILE0_31

The setting rejects MIME types without an installed encoder. The requested profile, level, resolution and rate must also be supported by that encoder. Playback selects the installed decoder from the received FourCC; the connect command advertises only available decoders. VP playback waits for a keyframe, reads its actual dimensions, and then waits up to five seconds for the decoder output surface.

The first encoded keyframe supplies the VP configuration fields. Initialization does not depend on optional encoder CSD. VP8 sends the eight-byte VP configuration record; VP9 sends the version-1 vpcC fields used by FFmpeg; playback also accepts bare eight-byte and version-prefixed nine-byte VP configuration records. ISO VP configuration bytes are never queued as Android decoder CSD or frames. The record's initialization-data length must be zero, as required for VP8/VP9 by the VP Codec ISO binding.

Codec changes involving VP8, VP9 or AV1, and changes to an active codec configuration, are rejected. Close playback before making those changes. Identical repeated headers are accepted. This does not add SRT/TS codec support or a new HDR publishing pipeline.
